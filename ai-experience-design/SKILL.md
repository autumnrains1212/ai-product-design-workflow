# AI产品设计与交付工作流

把需求规格与实际交付连起来：先明确产品要完成什么、如何验收，再完成用户授权的分析、设计、实现、检查和整理。默认连续执行；用户明确请求教学时才逐步讲解，不以反复选择题或阶段确认代替制作。

## 开始与推进

先读取[执行规程](references/requirement-to-delivery.md)，识别本轮是需求文档、设计原型还是完整可运行交付；尊重用户限定的只读、仅文档和既有项目范围。先检查已有材料与成果，再补缺，不重做已经完成的部分。

新产品、需求重整或完整交付时，读取[PRD 适配规则](references/ai-product-spec.md)，从[可编辑需求模板](assets/ai-native-prd-template.md)提取适用章节，形成项目需求基线并用它验收。用户只需提供一段需求，不必先填完模板；有依据的内容直接整理，未知信息标记为假设、待验证或待确认。小范围修改只更新受影响的规格与验证，不强制生成十二章文档。

[HTML 阅读与打印版](assets/ai-native-prd-template.html)与 Markdown 提供同一套需求内容；占位符和示例是填写帮助，不是当前产品的事实或需求。模板、执行规程和项目实测记录分别承担规格、制作与证据的职责。

一般实现选择自行决定。影响核心目标、不可逆数据处理、外部成本或访问权限的缺口提出最少必要问题，同时推进不依赖答案的工作。沿用用户已选平台、工具、参考、技术和授权；不把完整流程扩展成未授权的发布、发送或收费。

## 按需加载方法

- 需求提取、事实与未知、功能和操作语义评审：读取[需求分析与评审](references/workflow-01.md)。
- 上下文、模型流程、输出执行、安全、性能、成本和上线规格：读取[AI 产品规格适配与检查](references/ai-product-spec.md)，按需查模板 06–11 章。
- 可编辑设计、状态分支、组件与原型：读取[设计与交互落地](references/workflow-02.md)。网页 UI 先读[风格选择](references/web-style-selection.md)和[共享基础](references/web-ui-foundations.md)，默认按需求加载一个主风格：Ant、Clean、Editorial、Friendly、Enterprise 或 Agentic；明确要求比较时按需读取候选。用户明确要求、已有品牌与设计系统优先。使用具体设计工具时遵循其专门技能。
- 可运行实现、接口集成、数据一致性及运行测试：读取[端到端交付](references/end-to-end.md)，按产品实际行为选择实现，不预设数据库、异步任务或特定界面。
- 生成、检索、提取或工具决策的实际表现与回归：读取[输出质量](references/output-quality.md)，可用 `assets/evaluation-record.csv` 记录样本与证据。
- 真人验证：读取[用户验证](references/usability-testing.md)，使用 `assets/usability-record.csv`；无参与者时完成准备并保留待验证项。

## 完成边界

按执行规程逐项报告实际产物和证据，区分设计、配置、运行、模型质量、真人效果与生产状态。静态文档不等于已实现，模拟不等于真实服务，AI 自测不等于用户研究。缺少访问或外部条件时交付可执行部分和明确的阻塞、恢复方法；不得悄悄删步骤宣布完成。

交付实际文件或设计位置、适用的启动/预览入口、已执行检查、限制和待办。保留用户数据，不无依据覆盖既有内容。项目的品牌、尺寸、样例、节点、地址和工具故障只写入该项目记录，不回写成通用默认规则。
