# 从需求规格到交付

## 识别授权范围与现场

用户可以只给一段需求。提取目标用户、触发场景、具体任务、成功条件、输入输出、平台、现有资产及限制。检查已有需求、设计、代码、数据和可用工具，记录来源。不能把访谈、接口能力、模型表现、指标或日期补成事实。

先根据用户目标选择本轮范围：

- 仅需求/分析：交付可评审的规格、依据、验收条件和未决事项，不制作未要求的界面或服务。
- 设计/原型：交付适用的流程、状态和可编辑成果，明确交互演示与真实业务能力的边界。
- 完整可运行项目：从规格推进到实现、运行检查、修复和交接，不停在文档或画板。
- 已有项目或局部修改：复用当前基线，仅改受影响的行为、材料与验证；只读要求持续有效。

一般偏好采用合理默认并记录，关键未知影响目标或执行权限时再问。产品内应有的确认、撤销和授权仍须设计；代理能连续制作，不代表产品可替用户静默执行。

## 将 PRD 作为需求基线

新产品或需求重整先读 `references/ai-product-spec.md`，按 `assets/ai-native-prd-template.md` 的适用内容建立项目 PRD。先写价值、用户、范围和核心路径，再补功能、AI 规格、异常及验收。已有 PRD 优先保留结构，只用模板补遗漏。

章节可合并，公共规则集中维护并在功能中引用。明确区分已知事实、工作假设、待验证目标和实测结果。对不适用的能力说明原因；不因模板出现 RAG、长期记忆、异步任务、支付或多角色而引入它们。关键验收应能追溯到需求或功能标识。

不要求用户先填写长问卷或逐章批准。先完成可逆分析与制作，再将真正影响后续的关键分歧交给用户。PRD 会随实现和验证更新，不能在开工后与实际行为分离。

## 按依赖推进

下面是覆盖清单，不是固定数量的文件或强制串行阶段。按范围合并产物；可从 `assets/delivery-ledger.md` 维护一份交付记录。

| 工作 | 实际产物与进入后续的条件 |
|---|---|
| 需求与依据 | 明确服务谁、解决什么、版本边界、来源和未知；有可验收的核心目标 |
| AI 分工与能力规格 | 写清模型、程序、用户各自职责；实际输入、输出、执行权限与失败处理已定义 |
| 关键可行性验证 | 用实际资料验证高影响未知；不可用的模型、服务或参与者列为依赖，不伪造结果 |
| 流程、状态与设计 | 覆盖业务实际存在的分支；需要 UI 时按目标平台制作和检查，不强制所有产品有界面 |
| 实现与集成 | 用户要求运行成果时连接必要服务、状态和数据；只在需求成立时增加持久化、并发或任务管理 |
| 测试、质量与修复 | 按 PRD 的验收条件执行实际检查，记录缺陷与复测；代码存在不等于通过，文档目标不等于实测 |
| 真人验证 | 有参与者时实施中性任务并记录；缺参与者可交付原型和测试准备，效果保持待验证 |
| 交接与上线准备 | 能定位、查看或启动成果；接口、配置、限制、指标和适用的回退方法可追溯 |
| 发布与效果评估 | 仅在用户授权且环境具备时部署或对外操作；上线和实际效果分别以运行证据与真实数据确认 |

## 执行与恢复

依据产品行为选择恢复规则：只读问答可能只需要重新查询或补充资料；异步任务需要分离任务结果与查询状态；外部写入需要检查授权、重复执行和真实回执；可编辑内容需要明确草稿、保存及冲突。具体见 `references/end-to-end.md`。

写入失败先读回现场。根据错误证据修复或使用受支持的替代方式，持续失败时停止该方法并记录恢复条件，不无限重放相同操作。保护用户已有数据；未经授权不改变既有账户、发布、发送、收费或删除数据。

模型不可用时可在用户范围内制作显式标注的模拟、接口契约和评估准备。模拟方式与实际实现状态分开记录，不能用期望输出、固定样例或评分规则声称真实模型合格。

按影响优先修复改变用户意图、错误事实、数据丢失、越权和不可恢复的问题。测试数量与范围由改动及风险决定，不为低影响修改添加形式化测试，也不以任意数量宣称验证充分。

## 完成与交接

报告本轮范围、实际成果位置、适用的查看/启动方式、执行过的检查与证据、已修复及遗留问题。分别列出模拟、假设、待验证、阻塞和范围外事项，并写清恢复需要的资料、权限或外部条件。

需求规格、设计结构、视觉检查、原型配置、实际运行、模型质量、真人效果和生产状态各自确认；不能互相替代。终点是完成已授权范围，外部依赖不抹去已完成工作，也不能被省略来宣布全部完成。
